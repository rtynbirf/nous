# ADR-0015: релиз несёт SBOM двух форматов и точный аттестуемый набор

Статус: принято (мандат владельца, чат 2026-11-10; тикет 0022) ·
Дата: 2026-11-10 · Решает: владелец

## Контекст

ADR-0003 отделил релиз от CI и завёл аттестацию за гейтом
`ENABLE_ATTESTATION=1` (SLSA Build L2), но релизил только docs-тарболл с
одним файлом сумм. Мировая практика 2025–2026 ушла вперёд: OpenSSF
рекомендует выпускать SBOM в обоих доминирующих форматах (CycloneDX и
SPDX) — они взаимодополняемы (безопасность/VEX у обоих, разные
экосистемы потребителей); CISA SBOM Minimum Elements (2026) требует
supplier, имя, версию, хэши, связи, автора и временную метку; GitHub
artifact attestations дают криптографический провенанс (Sigstore), а
учеба Scorecard-исследований 2025 показывает: подписанные релизы и
защита ветки реализованы в меньшинстве проектов. Разрыв «сделали
аттестацию одного файла, а не набора» — типовая дыра: аттестат без
сумм-манифеста не закрывает вопрос «что именно было в релизе».

## Решение

1. `scripts/gen_sbom.py` (stdlib-only) строит релизный SBOM в двух
   форматах — CycloneDX 1.6 и SPDX 2.3.1 — по tracked-файлам репо:
   карта из `git ls-files`, байты и хэши — с диска. Два разных кода
   отказа: `missing_on_disk` (в индексе, нет на диске) и
   `modified_vs_index` (git-blob-sha1 диска ≠ индекс) — чтобы не врать
   о причине (A2). Подкоманда `verify` пересчитывает инвентарь и сверяет
   оба файла: missing/changed/extra. SPРX-верификационный код пакета —
   SHA1 от конкатенации отсортированных SHA1 файлов (§3.9.2 SPDX 2.3),
   пересчитывается нашим verify.
2. `release.yml`: SBOM строится ПЕРВЫМ шагом — по чистому чекауту, до
   регенерации `llms.txt` (иначе regenerated-файл был бы отличен от
   индекса и честный гейт уронил бы релиз); `verify` — fail-closed,
   `SHA256SUMS.txt` пишется последним (покрывает тарболл и оба SBOM,
   кроме самого себя), затем 4 attest-шага (тарболл, оба SBOM, суммы)
   за гейтом, затем выкладка точного набора из 4 артефактов.
   `--allow-dirty` у `gen` — только для локальной разработки
   (modified_vs_index становится предупреждением;
   missing_on_disk фатален всегда); в релизе флаг не используется.
3. Тест `tests/test_release_sbom.py` делает инвариант живым: точный
   набор (загружаемое == аттестуемое == 4 имени), порядок сборки по
   шагам-создателям (не по последнему вхождению — детектор не ловит
   сам себя), roundtrip gen→verify на живом репо, различение двух кодов
   отказа на временной мини-репе.
4. `scripts/agent_readiness.py` — self-probe готовности репозитория к
   AI-агентам: 14 исполнимых проб по мировым практикам 2026
   (AGENTS.md-стандарт, llms.txt, пины SHA, persist-credentials:false,
   минимальные permissions, отсутствие опасных триггеров, гейт
   аттестации, SBOM двух форматов, порядок сумм, свежесть пинов,
   dependabot/CODEOWNERS, governance-триада, исполняемая карта тестов,
   лёгкий пояс на секреты). Провал любой пробы — ненулевой выход;
   проба встроена шагом в `ci.yml` (verify).

## ПОЧЕМУ ТОЛЬКО ТАК

- **Два формата, а не один.** Потребители SBOM разной природы
  (вендоры безопасности — CycloneDX; комплаенс/ISO 5962 — SPDX).
  OpenSSF прямо рекомендует оба; один формат = искусственный выбор за
  потребителя. Версии честные: CycloneDX 1.6 (текущая), SPDX 2.3.1
  (ISO/IEC 5962:2023); SPDX 3.0 отложен до появления stdlib-валидатора
  — выдавать невалидный 3.0 хуже, чем валидный 2.3.1 (A10).
- **Диск — истина, индекс — карта.** `git ls-files` читает индекс:
  файл может быть удалён с диска и остаться в индексе. Генерация по
  одному источнику молча соврёт бы; два кода отказа различают причины.
- **SHA256SUMS последним и аттестованным.** Манифест сумм связывает
  все артефакты в единую позицию доверия; аттестованный манифест
  позволяет потребителю проверить весь набор одной сигнатурой.
- **Точный набор как тест, а не договорённость.** «Загружаемое ==
  аттестуемое» — инвариант, который иначе ползёт при каждой правке
  workflow; тест красный — релиз не выпускается.
- **Self-probe вместо внешнего грейдера.** Внешние «agent-readiness»
  сканеры оценивают репо со стороны; их вердикт невозможно провалить
  изнутри. Проба живёт в репо, исполняется в CI на каждый push и
  падает вместе с телом — критерий приёмки, который может провалиться
  (урок 0001).
- **stdlib-only.** SBOM-инструмент в TCB сам стал бы зависимостью,
  требующей SBOM (рекурсия доверия). Минимальные форматы проверяются
  нашим verify; внешние валидаторы подключаются отдельной калибровкой
  пинов, когда потребуют.
