# ADR-0008: actions.lock внедряется позже (R6), сейчас — SHA-пин

Статус: принято (отложено) · Дата: 2026-10-29 · Решает: владелец

## Контекст

GitHub документирует workflow dependency lockfiles (`.github/workflows/actions.lock`,
генерируется `gh actions-lock`): пин каждого action включая транзитивные
зависимости + owner_id, верифицируемый в рантайме. Это сильнее SHA-пина:
защищает и от подмены репо/форка. Но формат требует CLI-расширения и
процедуры обновления.

## Решение

Сейчас: полные SHA-пины + тест-гейт (ADR-0004). В R6: внедрение
`gh actions-lock` как второй ступени, с процедурой обновления в спеке 01.

## ПОЧЕМУ ТОЛЬКО ТАК

- SHA-пин закрывает главный вектор (переподвиг тегов) простым, проверяемым
  тестом способом. По-другому нет: внедрять механизм, требующий нового
  инструмента, в фазе R0 — риск для базового контура ради периферийного
  выигрыша.
- Отложенное внедрение = управляемое: к R6 у контура уже есть пины с датами
  и процедура калибровки — lockfile встраивается в неё без ломки.

## ПО ДРУГОМУ НЕТ

- Ручной lockfile «по образцу»: неизвестно точное текущее поле-схема;
  рукописный файл, который не подтверждён `gh actions-lock`, — фальшивая
  карта, хуже её отсутствия (нарушение аксиомы карта=территория).
- Игнорировать lockfile навсегда: теряем защиту owner_id — не принято.

## Последствия

- R6 содержит тикет: установка `gh actions-lock`, генерация, включение в
  `verify.sh`, обновление ADR-0004 со ссылкой на этот ADR.
- До R6 пины по SHA — единственная, но достаточная ступень.
