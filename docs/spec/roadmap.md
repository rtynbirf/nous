# Дорожная карта НОУС-ФОРЖ

Порядок фаз обоснован зависимостями: сначала калибровка (без пинов нельзя качать),
затем обследование (без probe нельзя безопасно писать на хосте), затем обе ветки
сборки, затем верификация и закалка. Каждая фаза = партия тикетов в `tasks/open/`.

## R0 — Скелет (выполнено 2026-10-29)

Конституция, контракты субъектов, CI (verify/security/docs), release (отделён),
исполняемая карта (tests), рефлексы (scripts), manifests, tasks, state, ветка
`agents/execution`. Доказательства: зелёный `verify.sh`, коммиты v0.1.0.

## R1 — Калибровка: источники и пины — частично исполнена (v0.2.0, тикет 0001)

Исполнено (v0.2.0): URL/каналы/методы/даты в `manifests/pins.yaml` — секция `forge`
статусы `calibrated-url`; протокол TOFU закреплён (выдуманных хешей нет —
`docs/genesis/revision-0.md` §4-I2). Остаток (SHA256/fingerprint из первого реального
прогона) — тикет 0006. Резолв-скрипт `pin_action.sh` — работает с v0.1; сверка
CI↔пины — тест-гейт ADR-0010.

## R2 — Probe: обследование хоста — исполнена (v0.2.0, тикет 0002 → done)

Исполнено: `src/forge/probe/probe.sh` — все домены спеки 02, только чтение,
fixture-режим для CI, JSON+лог; `tests/test_forge_probe.py` (11 тестов на
фикстурах BIOS/UEFI) зелёные. Реальное железо — по тикету владельца.

## R3 — Windows-ветка форжа — код готов (v0.2.0); приёмка — первый прогон (тикеты 0003, 0006)

Исполнено: `src/forge/win/` (fetch-fido.ps1 с TOFU-пином и нормализацией языка
под Fido; build.ps1 — фазы fetch→extract→render→inject→build→verify;
autounattend.template.xml c WillWipeDisk=false и без секретов; forge.ps1 —
точка входа ТЗ §1). Тест-гейты `tests/test_forge_win.py` (25 тестов). НЕ
исполнено (честно): реальная сборка — oscdimg/ADK требует Windows-хоста
владельца.

## R4 — Linux-ветка форжа (равноправная) — код готов (v0.2.0); CI-сборка — forge.yml; приёмка — тикеты 0004, 0006

Исполнено: `src/forge/linux/build.sh` (fetch по пинам + SHA256SUMS-гейт +
TOFU → extract → render → inject → xorriso-гибрид спеки 04 → verify);
шаблоны debian12.preseed и ubuntu-24.04 autoinstall (без секретов);
`tests/test_forge_linux.py`. CI-исполнение — `forge.yml` (ADR-0009):
ночью и вручную. Первый реальный прогон = TOFU-фиксация пинов (0006).

## R5 — Верификация и релизный контур — верификатор артефакта готов (v0.2.0); остальное — R6

Исполнено: `src/lib/verify-iso.sh` — гейты спеки 05 (размер/сектор, El Torito
BIOS+UEFI, injected-файлы, SHA256SUMS рядом с артефактом); вызывается
конвейерами обеих веток и forge.yml. Лог-протокол — фазы `nous::phase`.
Остаток: ротация логов, state-снимки после каждой фазы — R6 (0007).

## R6 — Закалка и (опционально) публикация — тикет 0007

Задачи: QEMU-смоук ISO (серийная консоль), zizmor `--persona=auditor`,
release-please (SemVer из Conventional Commits), uv lock-файл для requirements
(hash-pinning), copier-шаблон `templates/` (репо порождает репо),
OpenSSF Scorecard + перевод репо в публичные — **только** по явному решению
владельца (safe-default: `repo_visibility=private`).
Пересмотрено ADR-0010: `gh actions-lock` не внедряется — pins.yaml единственный
lockfile со сверкой тестом; вопрос переоткрывается при транзитивных зависимостях.

## Риски и их обработка

| Риск | Фаза | Обработка |
|---|---|---|
| Источник умер/изменился | R1+ | пин с датой; калибровка; тикет |
| Недоступна CI-сборка ISO (нет Windows-runner) | R3 | статические тесты в CI; сборка на хосте владельца по тикету |
| Дрейф пинов | все | `state/` фиксирует свежесть; Renovate (R6) |
| Секреты в логах | R5 | gitleaks в CI + маскирование в протоколе лога |

## ПОЧЕМУ ТАКОЙ ПОРЯДОК

Без R1 конвейер качает непроверенное; без R2 пишет в непонятую среду; R3/R4
независимы сознательно (+ЛИНУКС равноправен); R5 собирает доказательства для
приёмки; R6 закаляет то, что уже живёт. Другой порядок ломает зависимость
«калибровка → обследование → сборка → доказательство».
