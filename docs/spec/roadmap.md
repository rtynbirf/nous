# Дорожная карта НОУС-ФОРЖ

Порядок фаз обоснован зависимостями: сначала калибровка (без пинов нельзя качать),
затем обследование (без probe нельзя безопасно писать на хосте), затем обе ветки
сборки, затем верификация и закалка. Каждая фаза = партия тикетов в `tasks/open/`.

## R0 — Скелет (выполнено 2026-10-29)

Конституция, контракты субъектов, CI (verify/security/docs), release (отделён),
исполняемая карта (tests), рефлексы (scripts), manifests, tasks, state, ветка
`agents/execution`. Доказательства: зелёный `verify.sh`, коммиты v0.1.0.

## R1 — Калибровка: источники и пины

Тикеты: 0001 (архитектор). Задачи:
1. Проверить живость и официальный статус каждого источника спеки 01; зафиксировать
   в `manifests/pins.yaml`: URL, метод проверки, SHA256/версия, дата.
2. Резолв-скрипт для actions (`pin_action.sh`) — прогнать и сверить пины CI.
3. ADR: стратегия обновления пинов (ручная калибровка → Renovate для tools).

**DoD:** каждый источник имеет пин с датой; `verify.sh` проверяет целостность
manifests (ключи, формат, непустые SHA).

## R2 — Probe: обследование хоста

Тикеты: 0002 (архитектор → сборщик). Задачи:
1. Спека probe-модуля: OS/версия, железо (CPU/RAM/диски/сетевые), BIOS vs UEFI,
   свободные ёмкости, каталог вывода, права.
2. Реализация `src/forge/probe/` + тесты на фикстурах (без реального железа).
3. Выход: машиночитаемый отчёт (JSON) + человекочитаемый лог.

**DoD:** probe работает на фикстурах в CI; на реальном хосте — по тикету владельца;
безопасен (только чтение).

## R3 — Windows-ветка форжа

Тикеты: 0003 (forge-builder-win). Задачи:
1. Получение образа: официальный канал (спека 03), пин+SHA256.
2. Генерация `autounattend.xml` с безопасными дефолтами (wipe=false, локальная
   учётка при офлайне — спека 06).
3. Сборка ISO: DISM-модификация + oscdimg `-bootdata` (BIOS+UEFI).
4. Тесты структуры и конфигураций на фикстурах.

**DoD:** команда собирает ISO в целевой среде; артефакт с SHA256 и логом;
CI гоняет статические тесты; реальная сборка — по тикету владельца.

## R4 — Linux-ветка форжа (равноправная)

Тикеты: 0004 (forge-builder-linux). Задачи:
1. Источник netinst (с firmware для Debian 12), пин+SHA256.
2. preseed с безопасными дефолтами; локализация; без автостирания.
3. Сборка гибрида xorriso (BIOS+UEFI), изолируется в temp-каталоге.
4. Тесты на фикстурах.

**DoD:** аналогично R3; ветка развивается независимо (не блокируется R3).

## R5 — Верификация и релизный контур

Тикеты: 0005 (верификатор + архитектор). Задачи:
1. Верификация артефактов: SHA256, эл-торито-структура, наличие загрузочных записей
   (spекa 05), сверка с probe-ожиданиями.
2. Лог-протокол: единый формат лога фаз, ротация, отсутствие секретов (gitleaks).
3. Снятие снимков `state/` после каждой фазы.

**DoD:** конец фазы R3/R4 автоматически порождает верификацию; отчёт содержит
сырые выводы; тикеты закрываются только по вердикту верификатора.

## R6 — Закалка и (опционально) публикация

Задачи: release-please (SemVer из Conventional Commits), Renovate-конфиг,
`gh actions-lock` (ADR-0008), copier-шаблон `templates/` (репо порождает репо),
OpenSSF Scorecard + перевод репо в публичные — **только** по явному решению
владельца (safe-default: `repo_visibility=private`).

## Риски и их обработка

| Риск | Фаза | Обработка |
|---|---|---|
| Источник умер/изменился | R1+ | пин с датой; калибровка; тикет |
| Недоступна CI-сборка ISO (нет Windows-runner) | R3 | статические тесты в CI; сборка на хосте владельца по тикету |
| Дрейф пинов | все | `state/` фиксирует свежесть; Renovate (R6) |
| Секреты в логах | R5 | gitleaks в CI + маскирование в протоколе лога |

## ПОЧЕМУ ТАКОЙ ПОРЯДОК

Без R1 конвейер качает непроверенное; без R2 пишет в непонятую среду; R3/R4
независимы сознательно (+ЛИНУКС равноправен); R5 собирает доказательства для
приёмки; R6 закаляет то, что уже живёт. Другой порядок ломает зависимость
«калибровка → обследование → сборка → доказательство».
