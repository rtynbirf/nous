# 07 — Диспетчеризация субъектов

Субъекты: все · Фаза: сквозная · Протокол: `tasks/README.md`, [ADR-0007](../../decisions/0007-agents-branch-dispatch.md)

## Кто кому подчиняется

Владелец (`rtynbirf`) — единственный источник воли и подтверждений. Субъекты
исполняют тикеты в рамках контрактов. Ревью конституции — владелец (CODEOWNERS).
Верификатор — единственный принимающий тикеты; хронист — единственный
переносящий их в `done/`.

## Поток работ

```
владелец → тикет tasks/open/NNNN (роль, цель, границы, приёмка, ПОЧЕМУ)
субъект  → git checkout agents/execution → ветка agents/<роль>/<NNNN>-<slug>
субъект  → исполнение → verify.sh зелёный → PR в agents/execution
верификатор → сверка карты с территорией → вердикт
хронист  → перенос tasks/open → tasks/done (по вердикту) + state-снимок
владелец → периодический merge agents/execution → main (конституция)
```

## Формат тикета

Файл `tasks/open/NNNN-<slug>.md`, нумерация сквозная (N+1 за последним).
Обязательные секции: Роль · Цель (измеримая) · Границы (пути) · Критерии приёмки ·
ПОЧЕМУ ТОЛЬКО ТАК · Предусловия. Шаблон issue-диспетчера: `.github/ISSUE_TEMPLATE/task.md`.

## ПОЧЕМУ ТОЛЬКО ТАК

1. **Тикет-файл, а не устная задача.** Файл версионится, референсится в отчётах
   и ADR, переживает сессию агента. По-другому нет: контекст сессии умирает,
   файл — нет.
2. **Одна роль-исполнитель = один тикет.** Основной исполнитель указывается первым;
   вспомогательные роли (приёмка верификатором, фиксация хронистом, state-снимок)
   — в секции «Роль» после исполнителя и не меняют границ. Параллельность
   достигается параллельными тикетами с непересекающимися границами.
3. **Верификатор отдельно от исполнителя.** Сборщик не принимает свою работу:
   встроенный конфликт интересов (см. спеку 05).
4. **Ветка исполнения отделена от main.** Конституция не меняется в процессе
   исполнения; слияние — осознанный акт владельца после верификации.

## Правила отчёта (единый протокол субъектов)

1. Ссылка на тикет и ветку; список изменённых файлов + `git diff --stat`.
2. Сырые выводы ключевых команд (verify, сборка, тесты) — не пересказ.
3. Соответствие критериям приёмки: пункт → доказательство.
4. Явная граница: что не проверено и почему.
5. Расхождение с конституцией, замеченное в работе, — отдельный тикет, не
   «попутное исправление».

## Критерии приёмки системы диспетчеризации

1. Каждый тикет в `open/` ссылается на фазу roadmap и роль из контрактов.
2. Тест структуры проверяет: нумерация непрерывна, обязательные секции есть.
3. Ни один тикет не закрывается без вердикта верификатора (правило, проверяемое
   ревью — автоматизация в R6).
